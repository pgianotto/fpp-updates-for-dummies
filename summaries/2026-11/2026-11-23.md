# FPP Updates — November 23, 2026

*Unofficial, AI-written summary of the day's commits to FPP master. See the [commit log](https://github.com/FalconChristmas/fpp/commits/master) for the details.*

5 commits: four fixes and a safety check from Daniel Kulp, plus a MultiSync fix from darylc, touching the Scheduler, the Command Editor, output reloading, media logging, and the BeagleBone 64 flasher.

## Scheduler

- Fixed a bug where a schedule row pointing at a playlist or sequence that no longer exists (deleted, renamed, or copied in from another player) could break the whole Scheduler page — later rows wouldn't load and their start/end time pickers would disappear. The missing item now shows up as "Name (missing)" with a warning icon instead of crashing the page, and picking a different playlist clears the warning.

## MultiSync and updates

- The Command Editor no longer freezes for over two minutes when one of your MultiSync hosts is offline or unreachable. Loading each host's argument list used to block the page while waiting on that host; it now loads in the background with a short timeout, so an unreachable host just gets skipped instead of locking up the editor. (darylc)

## Outputs and hardware

- The BeagleBone 64 eMMC auto-flasher now runs a memory test before flashing, and refuses to flash a board whose RAM fails that test. Previously a board with bad memory could flash successfully and look fine, only to behave unpredictably later.

## Stability fixes

- Fixed a timing bug where saving an output configuration change right after a test or sequence stopped could briefly freeze FPP's main process, sometimes causing the Display Testing page to show an error instead of the test status.
- Reduced log spam: playlists that alternate clips with and without audio were writing extra log lines on every single loop pass. Those routine open/close lines are now quieter; an actual problem closing a stream still gets logged normally.

## Upgrade note

If you maintain BeagleBone 64 boards with a scripted or unattended eMMC flashing process, a board with a failing RAM test will now be rejected by the flasher (blinking LEDs, console shell) instead of completing silently. This is intentional — it catches bad hardware earlier — but it means a previously "successful" unattended flash on marginal hardware may now report failure.
