# FPP Updates — November 17, 2026

*Unofficial, AI-written summary of the day's commits to FPP master. See the [commit log](https://github.com/FalconChristmas/fpp/commits/master) for the details.*

18 commits, all from Daniel Kulp. The day's work is almost all under the hood: a fix for stale/incorrect pixel colors on BeagleBone-based PRU outputs, smoother video transitions in playlists, and a broad sweep of CPU-usage trims across playback, pixel overlays, the status API, and logging.

## Playback and playlists

- **Switching videos in a playlist no longer blacks out the screen or flashes the console underneath for a moment.** The display itself now stays up between clips while each video's own pipeline comes and goes, holding the last frame until the next video's first frame is ready. On a Pi 5 looping 1080p video this cut a roughly 300-350ms blank/console flash down to nothing.
- **The next video in a playlist — including the first video of an inserted playlist, such as a Remote Falcon song request — now starts decoding and getting ready about 1.5 seconds before the current one ends**, instead of starting cold. Together with the display change above, a looping video now wraps in about one frame interval instead of several hundred milliseconds of frozen or blank screen.
- **A video with sound now holds its last frame for less time when stopping (about 200ms instead of 400ms on a tested Pi 5)**, by skipping an unnecessary silence-flush delay when the audio was already being handled elsewhere.

## Outputs and hardware

- **Fixed stale or flickering pixel colors on BeagleBone-based PRU outputs** (BBB48String, affecting both AM335x boards and newer AM62x boards like current BeagleBone/PocketBeagle hardware). The CPU's cache could hold back the last few pixels of a frame (around pixels 327-329 of a port, with 25-28 outputs configured) and send stale color data to the PRU for a frame or more at every color change. The affected memory is now mapped so the CPU can't cache it, and a proper memory barrier makes sure a frame's data actually lands before the command that tells the PRU to use it. (Fixes #3200)
- **Removed leftover memory-flush calls on BBBMatrix and BBShiftString outputs that weren't actually doing anything**, cutting their per-frame CPU cost substantially — on a 6x6 panel matrix of 64x32 P5 panels, that dropped from 1.46ms to about 5 microseconds per frame, and overall fppd CPU use from 36% to 33% on a PocketBeagle.

## Performance improvements

- **Video frames handed to a Pixel Overlay Model are now swapped into place instead of copied**, saving around 6ms per frame on slower boards (tested on a BeagleBone AM335x) when playing video with a pixel overlay running.
- **Sequence and effect playback now reuses frame buffers instead of allocating and freeing a new one for every single frame**, avoiding memory-management slowdowns that could add several milliseconds per frame on some boards.
- **Scrolling Text overlays with an animated color effect (like Chase) now only recolor the part of the message actually visible on your model**, instead of redoing the whole message on every scroll step — a big speedup for long scrolling messages.
- **Reading a Pixel Overlay Model's data through the API** (used by some plugins and integrations) **no longer blocks other overlay effects or channel output while the response is being built.**
- **The web-based Virtual Display preview encodes changed pixels much faster** while you have it open in a browser — measured up to roughly 10x faster on BeagleBone-class hardware and over 20x on newer computers.
- **The status info FPP reports to the web UI, OLED display, remotes, and MQTT builds faster**, by caching the slower-changing parts (sensors, identity info) for up to a second and working out the next scheduled playlist only once per request instead of several times — roughly halving typical status-build time on tested boards.
- **Checking a Raspberry Pi for under-voltage/throttling warnings now happens at most once a second** instead of on every idle loop, trimming needless overhead while a show is playing.

## Stability fixes

- **Tamed two sources of log spam that could crowd out genuinely useful history in the crash-diagnostic log**: high-frequency MultiSync sync packets, unconfigured E1.31/ArtNet universe traffic, and full MQTT status payloads are now logged at a quieter level, and the "bridging while playing" warning now refreshes at most once a second instead of on every incoming packet.
